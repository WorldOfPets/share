## 1. Что и в каком виде сдается

Выбрать **одну** форму отчетности:

- **Конспект** — структурированный текстовый документ написанный от руки на бумаге (тема, ключевые понятия, примеры, выводы).
- **Файл с записями** — рабочий файл (`.md`, `.py`), в котором код из документации сопровождается комментариями.

Если выбран файл с записями, **каждый блок скопированного и запущенного кода** должен иметь комментарий, содержащий:
- **ФИО** студента;
- **дату**;
- **время** выполнения;
- **описание кода своими словами** (что делает каждая значимая часть).

**GitHub:** работа выгружается **ежедневно**. Оценивается не только итоговый файл, но и история коммитов: каждый учебный день — минимум один осмысленный коммит с понятным сообщением.

**Модификация:** итоговый код должен быть изменен на **20–30%** по сравнению с исходным примером из документации. Изменения сопровождаются письменным объяснением: **что именно изменено и зачем**.

## 2. Критерии оценки (20 баллов)

| № | Критерий | Показатель | Баллы |
|---|----------|------------|-------|
| 1 | **Наличие и полнота записей** | Конспект раскрывает тему; либо файл содержит все необходимые блоки кода. Материал структурирован, логичен, соответствует изученному разделу документации. | **0–2** |
| 2 | **Работоспособность скопированного кода** | Код из документации скопирован без искажений и **запускается** (подтверждение: скриншот вывода, лог, отметка в комментарии). | **0–2** |
| 3 | **Качество комментариев и идентификация** | Каждый блок кода описан своими словами; в комментарии указаны ФИО, дата и время. Описание отражает понимание, а не пересказ синтаксиса. | **0–2** |
| 4 | **Ежедневная работа с GitHub** | История коммитов показывает работу **каждый учебный день**; сообщения коммитов осмысленны; нет «свалки» одного итогового коммита. | **0–2** |
| 5 | **Модификация кода (20–30%) и обоснование** | Код изменен в заявленном объеме; письменно объяснено, **что** изменено и **зачем**; изменения корректны и не ломают работоспособность. | **0–2** |
| 6 | **Ответы на вопросы** | Свободно отвечать на вопросы по документации. | **0-10** |

**Шкала перевода в оценку (пример):**
- 16-20 баллов — «отлично»;
- 0–16 балла — «неудовлетворительно» (требуется доработка).

Критерий 1, 3 и 4 может быть заменен на «Конспект» для тех, кто выбрал текстовую форму: в этом случае оценивается полнота раскрытия темы и наличие собственных выводов, а не файл с кодом. Остальные критерии (2, 5 и 6) применяются к практической части в любом случае.

## 3. Пошаговый пример работы (как должен выглядеть один учебный день)

Ниже — пример для темы «Первый тест по документации Playwright»

### Шаг 1. Выбрать фрагмент документации и скопировать код

```python
# ФИО: Иванов Иван Иванович
# Дата: 2026-11-09
# Время: 14:30
# Описание: Этот код запускает браузер Chromium, открывает страницу
# playwright.dev и проверяет, что заголовок страницы содержит слово "Playwright".
# Я скопировал пример из раздела "Writing tests" и запустил его локально.

from playwright.sync_api import sync_playwright

with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.goto("https://playwright.dev/")
    print(page.title())
    browser.close()
```

### Шаг 2. Запустить и зафиксировать результат
```
# Результат запуска: "Fast and reliable end-to-end testing for modern web apps | Playwright"
# Код выполнен без ошибок.
```
(Можно приложить скриншот)

### Шаг 3. Ежедневный коммит на GitHub
```
day1: скопирован и запущен первый пример из документации Playwright
```
История коммитов — доказательство ежедневной работы.

### Шаг 4. Модификация кода (20–30%) и объяснение

```python
# ФИО: Иванов Иван Иванович
# Дата: 2026-11-10
# Время: 15:10
# Описание изменений: Я изменил исходный пример.
# 1. Добавил ожидание загрузки страницы (wait_for_load_state), чтобы тест был стабильнее.
# 2. Заменил print на assert, чтобы код не просто выводил заголовок, а проверял условие.
# 3. Добавил комментарий к изменению — это составляет примерно 25% изменения исходного кода.
# Зачем: исходный пример только демонстрировал открытие страницы; мой вариант приближен к реальному тесту.

from playwright.sync_api import sync_playwright

with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.goto("https://playwright.dev/")
    page.wait_for_load_state()  # добавлено: ожидание полной загрузки
    title = page.title()
    assert "Playwright" in title, f"Ожидалось 'Playwright' в заголовке, получено: {title}"  # изменено: проверка вместо print
    browser.close()
```

### Шаг 5. Коммит с модификацией
```
day2: модифицирован пример (wait_for_load_state + assert), добавлено обоснование
```

### Шаг 6. Повторять цикл ежедневно
Каждый следующий день:
1. Новый фрагмент документации → копирование → запуск → комментарий с ФИО/датой/временем.
2. Коммит.
3. Отдельный модифицированный пример с объяснением.
4. Коммит.
